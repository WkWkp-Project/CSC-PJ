# WakuFlow AI CS（Tulip）実行計画 — ฉบับทำได้จริง

เวอร์ชัน: 2026-09-16 / ตั้งต้นจาก「調査依頼書 2026-09-16」
สถานะ: แผนปฏิบัติ (ยังไม่ใช่สเปคปิดจบ / ยังไม่ตัดสินใจสร้าง)
ขอบเขต: Tulip เท่านั้น — Facebook Messenger + LINE 2 กลุ่ม (Wakuwaku / Brand) + Public Comment + Knowledge source

## 0. หลักการของแผนนี้ (อ่านก่อน)

แผนนี้ยึด 3 ข้อ เพื่อไม่ให้ล้มตอนลงมือจริง:

1. **ข้อมูลก่อน ระบบทีหลัง** — ห้ามเริ่มสร้างฟีเจอร์ก่อนรู้ว่าเคสจริงหน้าตาเป็นยังไง
2. **สมมติว่าดึงข้อมูลเก่าไม่ได้ จนกว่าจะพิสูจน์ว่าได้** — นี่คือความเสี่ยง #1 ของงานนี้ (ดูข้อ 3)
3. **แยก "ทำได้ทางเทคนิค" ออกจาก "ทำได้ตามนโยบาย/สิทธิ์"** — Meta/LINE หลายอย่างทำได้เชิงโค้ด แต่ผิด policy หรือไม่มี permission

ทุกเฟสมี **Gate** — ถ้าไม่ผ่าน gate ห้ามข้ามไปเฟสถัดไป

## 1. ภาพรวมเฟส

| เฟส | ชื่อ | ผลลัพธ์ | Gate ผ่านเมื่อ |
| --- | --- | --- | --- |
| **0** | Access & Legal Check | รู้ว่าเข้าถึงอะไรได้จริง | ยืนยันสิทธิ์/เจ้าของบัญชี/วิธีดึงครบทุกช่องทาง |
| **A** | เก็บ + วิเคราะห์ประวัติ | 案件一覧 + สถิติจำแนก | ครอบคลุมเคสตัวแทน + เจอ "รู" งานคนแล้ว |
| **B** | PoC เทคนิคทีละช่องทาง | ผลตรวจ + ข้อจำกัดจริง | เส้นทางหลักไหลจบ / เส้นทางที่ไม่ไหลระบุชัด |
| **C** | ออกแบบ + คิดต้นทุน | สเปก minimum + ราคา | แยกงาน AI/โปรแกรม/คน + ต้นทุนตามปริมาณจริง |

ลำดับสำคัญ: **0 → A → B → C** ห้ามสลับ โดยเฉพาะห้ามทำ B (ต่อ API) ก่อน 0 (เช็คสิทธิ์)

## 2. Inventory ทุกช่องทาง + สิทธิ์ที่ต้องยืนยัน (เฟส 0)

ก่อนแตะข้อมูล ต้องกรอกตารางนี้ให้ครบ **ทุกช่อง** ห้ามเว้นว่างด้วยการเดา:

| ช่องทาง | เจ้าของ/ผู้ถือสิทธิ์ | สิ่งที่ต้องยืนยัน | ใครยืนยันได้ |
| --- | --- | --- | --- |
| **FB Page (Tulip) Messenger** | Tulip? / Wakuwaku? | ใครเป็น Admin เพจ, มี Business Manager ไหม, app ต่ออยู่แล้วหรือยัง | Wakuwaku + Tulip |
| **FB Public Comment** | เดียวกับเพจ | ตอนนี้ใครดูแล, มี keyword filter อยู่แล้วไหม | ผู้ดูแลเพจ |
| **LINE กลุ่ม Wakuwaku** | Wakuwaku | เป็น group/multi-person chat, มี OA อื่นอยู่ในกลุ่มไหม | หัวหน้าทีม CS |
| **LINE กลุ่ม Brand** | Tulip | สิทธิ์เพิ่ม bot เข้ากลุ่ม, ใครเป็นคนตอบฝั่งแบรนด์ | Tulip |
| **Knowledge / Content** | Wakuwaku | มีเอกสารสินค้า/FAQ อยู่ที่ไหน รูปแบบอะไร | ทีม Content |
| **ประวัติเก่า (ทุกช่องทาง)** | — | ดึงย้อนได้ถึงเมื่อไหร่ ด้วยวิธีไหน | ต้องทดสอบจริง (ดูข้อ 3) |

**เอาต์พุตเฟส 0:** ตารางข้างบนกรอกครบ + ระบุ "ช่องที่ยังไม่รู้ ต้องถามใคร"

## 3. ความเป็นไปได้ของการดึงข้อมูล — ตัวจริง (หัวใจของความเสี่ยง)

> อันนี้คือส่วนที่คุณสั่งว่า "ความเป็นไปได้ด้านการใช้ข้อมูล" — ขอเขียนตรงๆ ตามข้อจำกัดจริงของแพลตฟอร์ม ไม่ใช่ความหวัง

| แหล่ง | ดึง "ข้อความในอนาคต" (หลังต่อระบบ) | ดึง "ประวัติเก่า" (ก่อนต่อระบบ) | ไฟล์แนบเก่า | ข้อจำกัดจริงที่ต้องระวัง |
| --- | --- | --- | --- | --- |
| **FB Messenger** | ✅ Webhook (real-time) | ⚠️ Conversations API ดึงได้บางส่วน แต่ขึ้นกับ permission/สถานะเพจ | ❌ **URL รูปหมดอายุ** ต้องรีบโหลดเก็บ | ต้องมี `pages_messaging`, ผ่าน App Review, เพจต้องไม่ติด restriction |
| **LINE (ทั้ง 2 กลุ่ม)** | ✅ Webhook (real-time) | ❌ **ไม่มี API ดึงแชทกลุ่มย้อนหลังเลย** | ❌ ต้อง export จากแอปมือ | Bot อ่านได้เฉพาะข้อความ**หลังเข้ากลุ่ม**เท่านั้น |
| **FB Comment** | ✅ Webhook / Graph API | ⚠️ Graph API ดึง comment เก่าได้ | รูปใน comment มี URL หมดอายุ | policy การซ่อน/ตอบอัตโนมัติมีข้อจำกัด |

### ข้อสรุปตรงๆ ที่ต้องยอมรับตั้งแต่วันนี้:

1. **ประวัติ LINE เก่า = ดึงผ่าน API ไม่ได้** → ต้อง **export ไฟล์แชทจากแอป LINE ด้วยมือ** (ได้เป็น text, **สื่อ/รูปหลุด**) หรือ **screenshot** เคสตัวแทน
2. **ประวัติ Messenger เก่า** → ดึงได้บางส่วน แต่ **รูป/วิดีโอเก่า URL หมดอายุ** ถ้าจะเก็บต้องรีบทำ และอาจต้องพึ่ง Meta Business Suite export + งานมือ
3. เพราะฉะนั้น **เฟส A ต้องออกแบบให้ทำงานบนข้อมูลที่ export ด้วยมือได้** ไม่ใช่รอ API ดึงอัตโนมัติ
4. **แผนสำรอง (แนะนำให้ทำคู่กัน):** ต่อ webhook เก็บ "ข้อมูลใหม่" ตั้งแต่วันนี้ ควบคู่กับ export ของเก่า — เพราะยิ่งช้า ข้อมูลใหม่ยิ่งหาย

**Gate เฟส 0/3:** ทดลอง export จริง 1 รอบต่อช่องทาง แล้วบันทึกว่า **ได้อะไร / หายอะไร / ย้อนได้ถึงเมื่อไหร่** — ห้ามเขียนว่า "ดึงได้หมด" ถ้ายังไม่ได้ลอง

## 4. โครงสร้างข้อมูล & การจัดเก็บ

แยกชั้นข้อมูลให้ชัด เพื่อกันปนเปื้อนและกันข้อมูลหาย:

```
/raw            ← ต้นฉบับ read-only (export ดิบ, screenshot, ไฟล์แนบ) — ห้ามแก้
/normalized     ← แปลงเป็นโครงเดียวกัน (เวลาไทย + timezone เดิม, ผู้ส่ง, role)
/cases          ← 案件 (ร้อยเส้น Messenger↔LINE เป็นเคสเดียว)
/knowledge      ← FAQ/ข้อมูลสินค้า แยกตามสถานะ (ถาวร/เฉพาะราย/มีวันหมดอายุ)
/analysis       ← สถิติ, การจำแนก, ช่องว่างงานคน
```

**กติกาข้อมูลบังคับ:**
- เก็บ **ภาษาไทยต้นฉบับเสมอ** สรุป JP/EN แยกฟิลด์ ไม่ทับต้นฉบับ
- เวลาทุกอย่างแปลงเป็น **เวลาไทย** + เก็บ timezone เดิมไว้ด้วย
- ไฟล์แนบที่ URL จะหมดอายุ → **ดาวน์โหลดเก็บทันที** + บันทึกที่มา
- ข้อมูลที่หาย → เขียนว่า **"欠落・未取得 (ขาด/ยังไม่ได้)"** ห้ามตีความว่า "ไม่มีไฟล์แนบ"
- 1 เคส = 1 ID ร้อยข้าม Messenger → LINE → Messenger กลับ

## 5. ความเสี่ยงด้านข้อมูล + มาตรการ (Risk Register)

| # | ความเสี่ยง | ผลกระทบ | มาตรการ |
| --- | --- | --- | --- |
| R1 | **ประวัติเก่าดึงไม่ได้ / ดึงได้ไม่ครบ** | วิเคราะห์เพี้ยน, ประเมินงานคนต่ำไป | export มือ + เก็บข้อมูลใหม่ตั้งแต่วันนี้ควบคู่ (ข้อ 3) |
| R2 | **PII หลุด** (ชื่อ/เบอร์/ที่อยู่ลูกค้า) | ผิด PDPA, ความเชื่อมั่น | เก็บ PII เท่าที่วิเคราะห์ต้องใช้, mask ในไฟล์ที่แชร์, จำกัดสิทธิ์เข้าถึง /raw |
| R3 | **ข้อมูลข้ามแบรนด์ปนกัน** | ตอบผิดแบรนด์, ความลับรั่ว | 1 knowledge store ต่อแบรนด์, กันไม่ให้ context ปน, ทดสอบ boundary ด้วยข้อมูลจริง |
| R4 | **Prompt injection จากข้อความลูกค้า** | ลูกค้าสั่งให้ AI เปลี่ยนปลายทาง/สิทธิ์/กฎ | ถือข้อความลูกค้าเป็น "ข้อมูล" ไม่ใช่ "คำสั่ง", ปลายทาง/สิทธิ์ fix ในระบบ ไม่ให้ข้อความแก้ได้ |
| R5 | **รูป URL หมดอายุก่อนเก็บ** | หลักฐานเคลมหาย | pipeline โหลดเก็บทันทีเมื่อรับ, ไม่ผูกกับการวิเคราะห์ภาพ |
| R6 | **เอาคำตอบเก่าเข้ามาเป็น FAQ ทั้งหมด** | เผยแพร่ข้อมูลผิด/หมดอายุ/เฉพาะราย | แยกสถานะ (ถาวร/เฉพาะราย/มีวันหมดอายุ/ขัดแย้ง), ไม่ auto-import ทั้งก้อน |
| R7 | **AI ตอบเกินสิทธิ์** (รับปากเงื่อนไข, ยืนยันข้อเท็จจริงแทนแบรนด์) | ผูกพันธ์ทางธุรกิจ, เคลมบานปลาย | จำกัด scope AI, คำที่มีเงื่อนไข/ชดเชยต้องผ่านคน, AI เล่าเป็น "ลูกค้าแจ้งว่า..." ไม่ตัดสินเอง |
| R8 | **LINE 1 กลุ่ม = 1 Official Account** | bot เข้าไม่ได้ถ้ามี OA อื่นอยู่แล้ว | เช็คก่อนในเฟส 0 ว่ากลุ่มมี OA อื่นไหม |
| R9 | **export/ต่อ API โดยไม่ได้รับอนุญาตเจ้าของบัญชี** | ผิด policy Meta/LINE, บัญชีโดนระงับ | ยืนยันเจ้าของ + ขออนุญาตเป็นลายลักษณ์ก่อนแตะ |

## 6. เฟส A — เก็บ + วิเคราะห์ประวัติ (ผลงานชิ้นแรก)

**เป้า:** ได้ 案件一覧 (case list) + สถิติจำแนก + รู้ว่า "รู" งานคนอยู่ตรงไหน

ขั้นตอน:
1. **ยืนยันวิธี export ต่อช่องทาง** (จากเฟส 0/3) — เริ่ม 1 เดือนล่าสุด, ขยายเป็น 3 เดือนถ้าเคสน้อย/ไม่เจอ exception
2. **เก็บ raw** ทั้ง 3 ช่องทางในช่วงเวลาเดียวกัน + โหลดไฟล์แนบเก็บ
3. **Normalize** → เวลาไทย, role ผู้ส่ง, ความสัมพันธ์การตอบ
4. **ร้อยเป็นเคส** — จับคู่ด้วยชื่อลูกค้า/สินค้า/เวลา/ข้อความที่ถูก quote; ถ้าไม่ชัดให้ mark **"紐づけ未確認 (ยังไม่ยืนยันการเชื่อม)"** ห้ามเดา
5. **จำแนกประเภท** (ข้อมูลสินค้า / ราคา-โปร / สต็อก / เคลมคุณภาพ / ซื้อจำนวนมาก / ข้อมูลไม่พอ / อื่นๆ / ทักทาย-สแปม)
   - "มีรูป" = ฟิลด์แยก **ไม่ใช่หมวดหลัก** (เช่น "เคลม / มีรูป / อธิบายครบ / มีถามแบรนด์")
6. **แยกงานคนต่อขั้น**: เงื่อนไขเกิด / ข้อมูลที่อ้างอิง / งานที่ทำจริง / ใครตัดสิน / ส่งต่อไปไหน / เงื่อนไขจบ
   - แยก "outsource ตัดสินเอง" ออกจาก "แค่ส่งต่อคำสั่ง Wakuwaku/แบรนด์"
7. **สรุปสถิติ**: จำนวนเคส, ข้อความรับ, ตอบ, ไฟล์แนบ, ครั้งที่ถาม Wakuwaku, ครั้งที่ถามแบรนด์, เวลารอ, **งานคนที่เหลือ** — แยกความเห็น automate ตามหมวด ห้ามสรุปรวมว่า "เป็นข้อความ = automate ได้"

**Gate A:** อธิบายได้ว่า เคสตัวแทนแต่ละแบบ ใครตัดสินอะไร ส่งอะไรไปไหน และ **งานคนเหลือตรงไหน** (โดยเฉพาะงานคัดลอก/ส่งต่อ/ส่งรูปซ้ำ)

## 7. เฟส B — PoC เทคนิค ทีละช่องทาง

ทำ **เส้นทางหลักก่อน** แล้วค่อยตรวจจุดที่ทำให้หยุด ทดสอบบน **ข้อมูลย้อนหลัง + คู่สนทนาทดสอบ** — **ห้ามส่งข้อความจริงไปหาลูกค้าจริง**

| # | เคสทดสอบ | เส้นทางที่ต้องไหลจบ |
| --- | --- | --- |
| B1 | คำถามสินค้าปกติ | Messenger รับ → ตอบจาก knowledge → Messenger ส่ง |
| B2 | ถาม Wakuwaku | ส่ง LINE → ผูกคำตอบกลับเคส → ตอบลูกค้า |
| B3 | ต้องยืนยันกับแบรนด์ | Wakuwaku สั่ง → ถาม LINE แบรนด์ → รับคำตอบ → ตอบลูกค้า |
| B4 | **รูป + คำอธิบายครบ** | **ไม่ถามซ้ำ** → ส่งรูป+คำอธิบาย+เลขเคส เข้า LINE |
| B5 | รูปอย่างเดียว/อธิบายไม่พอ | ถามเพิ่ม → รับคำตอบ → ส่งรูป → ตอบลูกค้า |
| B6 | แก้ระหว่างรอ / หลายเคสพร้อมกัน | สะท้อนข้อมูลล่าสุด, ไม่ส่งคำตอบเก่า/ผิดเคส |
| B7 | **ไม่ตอบ/ส่งไม่ได้/ระบบล่ม** | พัก-เตือน-แจ้ง-ทำต่อได้, **ห้ามนับที่ยังไม่ส่งว่า "เสร็จ"** |
| B8 | อัปเดต FAQ | reuse คำตอบทั่วไปได้, ไม่เอาข้อมูลเฉพาะราย/มีวันหมดอายุไป generalize |

### จุดเทคนิคที่ต้องเจาะเป็นพิเศษ

- **B4 — ส่งรูป Messenger → LINE โดยไม่ให้คนดาวน์โหลด/forward ทุกครั้ง**
  แนวทาง: รับ attachment URL จาก webhook Messenger → relay โหลด → host เป็น HTTPS ที่ LINE ดึงได้ → ส่งเป็น image message เข้ากลุ่มด้วย group ID
  ต้องตรวจ: อายุ URL, สิทธิ์เข้าถึงรูป, LINE เปิดรูปได้จริง, การผูกรูป↔เลขเคส
  **ไม่ต้องเรียก AI วิเคราะห์ภาพ** สำหรับแค่ "ส่งต่อ"
- **B7 — ตอบ Messenger หลังแบรนด์ตอบช้า**
  นี่คือจุดตายของงานทั้งระบบ: เช็คว่ามีเคส "เขียนคำตอบได้ แต่ส่งไม่ได้" (เลย messaging window) ไหม และเงื่อนไข/เวลาที่ส่งอัตโนมัติได้ — อย่าปน "auto reply" กับ "มีคนตอบ"
- **LINE binding** — ผูกคำตอบที่ไม่มีเลขเคสกลับเข้าเคส + วิธีไม่อ่านแชทเล่นทั้งหมดแต่ไม่พลาดคำตอบจริง

**Gate B:** เส้นทางหลัก (B1–B5) ไหลจบในสภาพทดสอบ + จุดที่ยังไม่ไหล (B6–B8) ระบุสาเหตุ+ทางแก้ชัด พร้อม log/หน้าจอเป็นหลักฐาน + แยกระดับ (แค่เช็คสเปก / ทดสอบใน test env / ทดสอบใน Tulip จริง)

## 8. เฟส C — ออกแบบ + คิดต้นทุน

1. **แยกงาน**: AI / โปรแกรมธรรมดา / คน — โดยเฉพาะระบุงานคนที่เหลือ (คัดลอกคำตอบ, ส่งรูปซ้ำ ฯลฯ)
2. **วัดปริมาณจริง**: จำนวนเรียก AI/เคส, token เข้า-ออก, ส่ง LINE, เก็บ/ส่งไฟล์, ชั่วโมงคนที่เหลือ
3. **แยกต้นทุน**: ค่าพัฒนา+ติดตั้งครั้งแรก / ค่า AI จริง / ค่าเชื่อม-เก็บ-LINE / ค่าคนดำเนินงาน / ค่าดูแล-ปรับปรุงต่อเนื่อง
4. หลักการต้นทุน:
   - "AI รับ 24 ชม." ≠ เรียก AI 24 ชม. → ระหว่างรอเก็บ state ไม่กิน token
   - งานที่ไม่เรียก AI (รับ/เก็บ/ส่งต่อ/แจ้งเตือนสำเร็จรูป) = ไม่มี token แต่ **มีค่า infra/ส่ง**
   - **อย่าเอาราคา/เรต/สมมติฐานเก่ามาใช้เป็นต้นทุนจริง**
5. **อย่าตีค่างานคนที่เหลือเป็นศูนย์** เวลาเทียบกับค่า outsource เดิม (25,000 THB/เดือน)

**Gate C:** สเปก minimum ที่จะทำจริง + ต้นทุนอิงปริมาณจริง + เงื่อนไขเข้าสู่การใช้งานจำกัดใน Tulip

## 9. สรุป Go / No-Go

| Gate | เดินต่อได้เมื่อ | ถ้าไม่ผ่าน |
| --- | --- | --- |
| G0 | ยืนยันสิทธิ์+วิธีดึงครบทุกช่องทาง | หยุด ไปขออนุญาต/หาเจ้าของบัญชีก่อน |
| GA | มีเคสตัวแทน + เห็น "รู" งานคน | ขยายช่วงเวลา/เก็บเพิ่ม |
| GB | เส้นทางหลักไหลจบ + จุดตันชัด | แก้จุดตันก่อนออกแบบต่อ |
| GC | ต้นทุน+สเปกอิงข้อมูลจริง | ยังไม่เสนอราคา/ยังไม่ตัดสินแทน outsource |

**นิยาม "งานเสร็จ":** อธิบายได้ว่า Tulip มีคำถามจริงแบบไหน / เส้นทางไหนไหลได้ / เส้นทางไหนยังไม่ไหล / คนเหลือตัดสิน-ทำอะไร แล้วค่อยตัดสินว่าแทน outsource ได้เต็มตัวไหม

## 10. สิ่งที่ต้อง confirm ก่อนเริ่ม (ช่องว่างที่ยังไม่รู้)

ต้องถามให้ชัดก่อนลงมือ — เขียนไว้ว่า *ไม่รู้อะไร ถามใคร*:

1. ใครเป็นเจ้าของ/Admin **FB Page Tulip** และมี Business Manager/app ต่ออยู่ไหม → *Wakuwaku + Tulip*
2. **LINE 2 กลุ่ม** เป็น group แบบไหน มี OA อื่นอยู่แล้วไหม, ใครมีสิทธิ์เพิ่ม bot → *หัวหน้า CS / Tulip*
3. **ประวัติเก่าดึงย้อนได้ถึงเมื่อไหร่จริง** (ต้องลอง export 1 รอบ) → *ทีมเทคนิค*
4. เอกสาร **knowledge/FAQ สินค้า** อยู่ที่ไหน รูปแบบอะไร ใครดูแล → *ทีม Content*
5. นโยบาย **PII/PDPA** ภายใน — เก็บ/mask/แชร์ได้แค่ไหน → *ผู้รับผิดชอบข้อมูล*
6. ฝั่งแบรนด์ **ใครเป็นคนตอบใน LINE** และตอบช้าแค่ไหนโดยเฉลี่ย → *Tulip*

> ห้ามหยุดรอจนครบทุกข้อ — เริ่มจากเคสตัวแทนที่ได้ก่อน แล้วระบุช่องที่ยังไม่รู้ควบคู่ไป
